## 2. Release Keystore Security Policy

### 2.1 Why the Release Keystore is Critical
In the Android security model, the release signing key establishes the developer's cryptographic identity and app integrity.
- **Update Authorization**: Android OS strictly enforces that updates to an installed package must be signed with the identical private key (`PackageSignatures`).
- **Data Protection**: Keystore identity protects application sandboxes, Room SQLite databases, and shared user permissions.
- **Consequence of Key Loss**: If the production keystore or private key is lost or destroyed, **it is impossible to update the application**. Users would have to manually uninstall the app—destroying all locally persisted offline emergency SOS queues, warning logs, and peer routing states—and install a newly generated package.

### 2.2 Secure Storage & Custody Rules
1. **Never Commit to Git**: The `.keystore` or `.jks` file, passwords, and aliases must **NEVER** be committed to version control. Ensure `*.keystore` and `*.jks` are in `.gitignore`.
2. **Access Control**: Only designated Release Officers should hold access to the keystore.
3. **Environment Separation**: Do not use the default Android Studio debug keystore (`debug.keystore`) for production or field pilot releases.
4. **3-2-1 Backup Strategy**:
   - 3 separate copies of the keystore.
   - 2 different physical storage media (e.g., encrypted USB drive and secure cloud vault).
   - 1 copy stored in an offsite, air-gapped physical safe.

## 3. Step-by-Step Signing Procedure

When the release officer is ready to sign the unsigned APK generated by Gradle, execute the following verified procedure:

### Step 1: Generate Release Keystore (One-Time Setup)
```bash
keytool -genkeypair \
  -v \
  -keystore blackout-release.jks \
  -alias blackout-release \
  -keyalg RSA \
  -keysize 4096 \
  -validity 10000 \
  -dname "CN=BLACKOUT Emergency Network, OU=Operations, O=BLACKOUT Civil Defense, C=US"
```

### Step 2: 4-Byte Boundary Alignment (`zipalign`)
Before signing with `apksigner`, uncompressed data within the APK must be aligned on 4-byte boundaries to reduce memory consumption at runtime:
```bash
# Locate zipalign within Android SDK build-tools (e.g. 34.0.0)
zipalign -v -p 4 \
  app/build/outputs/apk/release/app-release-unsigned.apk \
  app/build/outputs/apk/release/app-release-aligned.apk
```

### Step 3: Cryptographic Signature via `apksigner`
Sign using APK Signature Scheme v2 and v3 (mandatory for Android 11+):
```bash
apksigner sign \
  --ks blackout-release.jks \
  --ks-key-alias blackout-release \
  --out app/build/outputs/apk/release/app-release-signed.apk \
  app/build/outputs/apk/release/app-release-aligned.apk
```
*Prompt will ask for Keystore Password.*

### Step 4: Verification of Signed APK
Verify that the signature schemes are valid and intact:
```bash
apksigner verify --verbose app/build/outputs/apk/release/app-release-signed.apk
```
**Expected Output**:
```
Verifies
Verified using v1 scheme (JAR signing): true
Verified using v2 scheme (APK Signature Scheme v2): true
Verified using v3 scheme (APK Signature Scheme v3): true
Number of signers: 1
```

## 4. Android App Bundle (AAB) Signing for Google Play

If deploying via Google Play Console with Play App Signing:
1. Upload `app/build/outputs/bundle/release/app-release.aab` directly to the Google Play Internal Testing track.
2. Sign the AAB with the upload key using `jarsigner`:
```bash
jarsigner -verbose \
  -sigalg SHA256withRSA \
  -digestalg SHA-256 \
  -keystore blackout-upload-key.jks \
  app/build/outputs/bundle/release/app-release.aab \
  blackout-upload-alias
```
3. Google Play will ingest the bundle and sign the generated split APKs using the managed Google Play App Signing key.

## 5. Device Installation & Verification

To verify the release APK on a physical pilot device via ADB:
```bash
# 1. Enable USB Debugging on target device
adb devices

# 2. Perform fresh installation of signed APK
adb install -r app/build/outputs/apk/release/app-release-signed.apk

# 3. Launch application and inspect system logcat for initialization
adb logcat -s "BlackoutApplication:*" "NearbyManager:*" "RoomDatabase:*"
```
Verify that:
- Runtime permissions dialogs appear for Nearby Devices and Location.
- Room SQLite Database opens successfully at schema version 4.
- Background WorkManager tasks (`AlertUploadWorker`, `WarningSyncWorker`) schedule without security exceptions.
